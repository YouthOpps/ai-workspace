# Opportunity Source Integration — Developer Agent

## Activation and task lock
Follow [workspace rules](../../AGENTS.md) and [issue workflow](../../docs/WORKFLOW.md). All agent communication, issue and PR text, documentation, code comments, and commits must be in **English**. Use the necessary independent Product Owner, Architect, Developer, DevOps Engineer and QA roles, with cross-review when available. Record material findings and cited decisions in the issue and relevant commit bodies. Work with concise evidence and minimal token usage.

This file **defines a reusable process only**. Editing skills in `ai-workspace` does not itself authorize source development. Activate only for a **separately assigned integration issue**. When activated, fetch `data-pipeline`'s latest `origin/main`, verify the fetched SHA and working-tree status, then create the issue-specific branch **from `origin/main`**, never from the pinned submodule commit. Preserve any pre-existing local changes rather than resetting them. Work inside the `data-pipeline/` Git repository. Its commit and PR belong to `YouthOpps/data-pipeline`, **not** `ai-workspace`; do not commit a changed submodule gitlink in the workspace.

1. Work on **one** specifically assigned GitHub issue; do not choose or modify others.
2. On activation, confirm that the assigned issue is open and labeled `in progress`. If needed, apply that label only as part of the separately authorized task. Do not silently switch tasks.
3. Treat the issue's acceptance criteria as the contract. Record source ID, publisher, official listing location, expected record types, and approved access method.
4. Develop and commit **only in `data-pipeline/`**. `data-source/` and `website/` submodules are read-only references during connector development. Production `data-source` records are written later **by the connector's GitHub Action after someone else merges the PR**; never commit to `data-source`, `website`, or the `ai-workspace` gitlinks as part of this integration task.

## Developer role — Integration Engineer

### Choose the connector runtime
- Evaluate **Node.js (JavaScript)** and **Python** for this specific publisher based on supported API/feed formats, parsing libraries, reliability, dependency footprint, performance, testability, maintainability and fit with the existing pipeline. Prefer the simplest viable solution; do not choose a language merely for variety.
- Record the chosen language and technical justification in the PR. Keep **one primary runtime per connector** unless a small, necessary interoperability bridge is justified by the current publisher/validation interfaces.
- **Node.js:** use the existing Node 22 project patterns, registered JS adapters, dependency lockfile, `node --test`, existing validation and Node setup in its dedicated Action.
- **Python:** create a focused Python adapter and isolated, pinned dependencies within `data-pipeline`; use a compatible Python runtime, Python unit tests and the dedicated Action's `actions/setup-python`. Integrate through a small, explicit interface to the current Node-based manifest/schema/collector/publication contract, rather than introducing a second divergent canonical schema or bypassing validators.
- Configure the connector's own Action to install **only the dependencies required** for that runtime, invoke that adapter with the source ID, apply the same rate controls and publishing contract, and fail visibly on any collection/validation error. Do not introduce new universal frameworks or language-specific duplication without evidence it is needed.

1. Inspect the full affected flow together: existing README and authoritative project documents, manifests (`data/sources/sources.json`, `source-registry.json`), adapter, dispatcher, `scripts/collect.js`, `scripts/publish-source.js`, catalog generator, Action, schemas and relevant existing tests. Identify shared contracts and impacts before coding. Make a coherent end-to-end correction, not an isolated workaround.
2. Verify the publisher's actual current site, source terms/robots and any API, feed, sitemap, paginated listings or approved alternative endpoint. An invalid/unavailable robots policy is **not** permission to scrape; resolve permission with the publisher or use an independently authorized official interface. Do not spoof identities, bypass CAPTCHAs, authenticate without authorization or work around access controls.
3. Capture real individual opportunities rather than generic pages, FAQ entries, directory landing pages, or fabricated records. Preserve official title, canonical URL, source attribution, category, countries and dates only where supported by evidence. Use stable record IDs; preserve first-seen history; deduplicate; keep missing eligibility/deadlines unknown, not inferred.
4. Reuse a suitable reviewed adapter where possible. If a source-specific Node or Python adapter is needed, wire it into the existing manifest/validation/publication entry points with focused positive, negative and fixture tests. Do not weaken shared validators or create a second incompatible output schema.
5. All HTTP entry points—including retries, redirects, nested link fetches, diagnostics and concurrent jobs—must use one origin-aware rate controller. Maximum **10 requests per rolling 60 seconds to the same target**, with at least 6 seconds between requests; honor `Retry-After`, 429, 503 and stricter server rules; use bounded exponential backoff, jitter and limited concurrency. Never hammer the upstream publisher. Avoid requests when fixtures suffice.
6. Emit schema-valid, 2-space-indented JSON with trailing newline via the existing publishing scripts. Preserve an existing valid snapshot if collection is empty, restricted or failed.
7. No speculative completion: repeatedly improve implementation based on QA rejection until objective acceptance is met or report an unresolved, documented block.
8. **Docs and lean tests:** Each connector is independently executed and should keep its source-specific guidance alongside its own implementation/configuration, with the **least documentation that fully explains access, behavior, data mapping and limitations**. Update all affected portions of existing authoritative documents in the same `data-pipeline` PR; prefer revising an existing document rather than adding duplicates. Reuse or extend existing tests, aiming for **one or two high-value connector-specific tests** (successful real mapping and key failure/edge behavior) alongside shared regression tests. More tests are justified only for genuinely distinct risks; do not write one test per implementation detail.
9. **Clean delivery:** remove temporary probes, test dumps, generated artifacts, debug logs, obsolete helpers, unused dependencies, unreferenced files/documents and redundant adapters introduced or made unnecessary by this change. Do not leave speculative backward-compatibility branches, compatibility shims or dead fallback code unless a currently supported consumer proves them necessary. Scope cleanup to this connector and files directly affected; never delete unrelated functionality or documentation without justification. Avoid unneeded output and large log dumps; favor targeted checks. Check `git diff`, staged files and dependency references before committing.

## Unsolvable integration (terminal outcome)
If documented investigation finds **no legally permitted and technically workable route to retrieve real opportunity records** (official API/feed, approved public listing, alternate official endpoint or publisher permission), do not fabricate records, enable a dead integration, or keep retrying indefinitely.
- Exhaust reasonable distinct options once, with evidence, bounded attempts and publisher-safe traffic. Do not interpret an inaccessible sandbox alone as proof of impossibility; follow the environment ladder in the QA skill.
- Add a detailed comment to the assigned GitHub issue covering tested URLs/methods, permission/robots findings, responses/errors, environments, dates, relevant logs, attempted remedies and why each route failed, plus a clear prerequisite that would unblock the integration. Do not disclose secrets.
- Mark the issue **unsolvable** using the repository's existing label/status convention (e.g. `unsolvable`; create a label only if separately authorized). Leave the issue open unless the project's explicit closure policy says otherwise. Stop work on it and report this outcome. Do not mark it successfully integrated or publish a placeholder.
- An unsolvable/never-integrated source **must not have published files created** under `data-source/sources/<connector-id>/`; it may remain in research/planning manifests.

## Independent Action and per-connector publication contract
- Every successfully integrated connector has **one independent** `data-pipeline/.github/workflows/fetch-<connector-id>.yml` GitHub Action, which invokes **only its matching adapter** using its selected Node.js or Python runtime and appropriate dependency installation. Shared publishing concurrency may serialize writes to prevent conflicts; no unrelated connector is fetched by that Action.
- Once the PR has been merged by its designated reviewer, the connector's Action fetches real, validated publisher opportunities and publishes its output to **`data-source/sources/<connector-id>/opportunities.json`**. Use the existing canonical schema and pretty-printed JSON with a trailing newline.
- The same connector has **`data-source/sources/<connector-id>/metadata.json`**, containing publisher/source metadata, the latest run `status`, `last_attempt_at` and **`last_success_at`** (time of the most recent successful retrieval of real validated data), using UTC ISO-8601 timestamps. The actual published record count and any supported provenance fields should remain accurate.
- On every Action run, update the **existing per-connector source manifest** at `data-source/sources/<connector-id>/metadata.json`. On success set `status: "ok"`, clear prior error details and advance `last_success_at` and `last_attempt_at` only after retrieving and validating real non-empty data. On failed fetch, parse, validation or publication, write `status: "error"`, `last_attempt_at` and sanitized, actionable `error` detail (including failure stage when known), while preserving `last_success_at`, `last_checked_at`, the previous record count and every last-good opportunity. Do not misrepresent a failed publication as success. The failure-status path must operate even after collection fails, without creating a never-integrated source folder; a metadata-write failure must remain visible.
- Rebuild `data-source/catalog.json` using the existing shared publisher on success **and on a recorded collection failure** so the matching entry in its `sources[]` reflects exactly the same status, error and last-attempt/success timestamps as the connector's `metadata.json`. Keep the catalog's last-good opportunity rows unchanged on failure. Stage/validate the complete affected dataset before one serialized publication commit; protect against partial writes, stale checkouts and conflicting publishers. On errors that prevent durable status publication, fail visibly and never claim the catalog was updated.
- **Do not create, update or rely on a root-level `data-source/sources.json` registry.** Its previously proposed status-index behavior is superseded. The only per-connector source status and last successful data retrieval record is `sources/<connector-id>/metadata.json`.
- Never create `sources/<connector-id>/` output for a candidate, blocked or unsolvable connector that has not successfully integrated. The pipeline's `data/sources/sources.json` remains the configuration/research manifest, not a published status registry.
- Test isolated Action execution, valid records, metadata status transitions, successful refresh with unchanged content, failed/empty response without data loss, safe retry/rate limiting and absence of unrelated source changes.

## Required developer-to-QA handoff
Provide exact changed paths, runtime choice and justification, legal/technical access evidence, inventory of real source opportunities and coverage explanation, observed source-to-output mapping, language-appropriate setup/run commands, tests/results, traffic counts and rate control strategy, dedup/freshness checks, clean-diff audit and remaining limitations. Never use record count alone to claim completeness.

## Verification and PR handoff — **do not merge**
1. Delegate/perform independent QA using `../integration-testing/SKILL.md`; the QA role decides acceptance, not the developer. Run existing pipeline checks and **runtime-specific tests in the current sandbox first**, including a controlled real-source collection when permitted. When sandbox network access is the only obstacle, use a permitted internet-connected environment. GitHub Actions are the **last resort for testing**, and any pre-merge test workflow must be isolated/non-publishing (no production data-source commit or token). Do not repeatedly fire production Actions as a substitute for debugging; never waive legal access or rate limits.
2. QA must verify actual records, correct schema/metadata, the source-specific Action configuration, and a clean diff with no unused files or compatibility baggage. On QA rejection, fix in the same source branch and repeat. If blocked or unsolvable, follow the issue outcome protocol; do not open a fake completion PR.
3. When QA approves, create/use **one branch for that issue inside `data-pipeline/`** (for example, `issue/<number>-<connector-id>`). Commit only the integration's code, tests, manifest changes, required dependencies and its `fetch-<connector-id>` Action to `YouthOpps/data-pipeline`; push that branch.
4. Open **one PR in `YouthOpps/data-pipeline` targeting `main`**, with the GitHub issue number and source ID in the title (e.g. `[#123] Integrate <connector-id>`). In the description link the issue with `Refs #123`, explain the runtime choice, permitted publisher access, records tested, QA evidence, rate limiting, affected paths and remaining risks. Link the PR in the issue and leave the issue open/in progress for review. Update the issue at meaningful milestones; include source references in the issue and applicable commit bodies. Avoid an auto-closing keyword unless the maintainers explicitly request it.
5. **Stop at the open PR. Do not merge, squash, rebase into `main`, delete the issue branch, close the issue or trigger a production publication.** After an authorized maintainer merges and acceptance is verified, that maintainer or authorized automation closes the issue and deletes the obsolete issue branch. Another maintainer performs the merge. The scheduled/approved Action publishes `data-source/sources/<connector-id>/` JSON and catalog **after merge**; any post-merge production verification is a separate authorized task. Do not commit data outputs or submodule pointer changes in `ai-workspace`.
6. Final response for a successful task is the PR URL plus QA/test summary. If upstream permission is pending, keep the issue blocked; if lawful avenues are exhausted, document and mark the issue unsolvable. Never claim publication or completion merely because the PR was opened.
